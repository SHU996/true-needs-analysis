# True Needs Deep（真需求深度分析）

> 来源框架：梁宁《真需求》（新星出版社，2024）
> 这是 true-needs-analysis 工具包的第二步——系统性深度体检。

## 核心原则

```
快速过滤告诉你"能不能做"
深度分析告诉你"做得对不对、护城河够不够深"
```

如果 true-needs-filter 是急诊分诊，true-needs-deep 就是全面体检。这个skill会对需求做三个维度的系统性检验。

## 使用前提

**在以下情况运行本 skill：**
- ✓ 用户明确要求深度分析："帮我深入分析"、"做个体检"、"详细分析一下"
- ✓ 用户已通过 true-needs-filter 快速过滤，想要进一步分析
- ✗ 用户只想要快速判断 → 建议使用 true-needs-filter
- ✗ 用户问"怎么做" → 不要拦截，直接帮他做

## 运行流程

### 第一步：三要素精度检验

逐项检查用户描述中的三个要素是否足够具体：

| 要素 | 检验标准 | 当前描述 | 是否达标 |
|------|--------|--------|--------|
| **用户** | 具体到能去找到这个人 | （填入用户描述） | ✓ / 需要更具体 |
| **场景** | 时间、地点、触发条件明确 | （填入用户描述） | ✓ / 需要更具体 |
| **痛点** | 说得出具体什么东西坏掉了 | （填入用户描述） | ✓ / 需要更具体 |

**对于每个"需要更具体"的要素，追问一次**，直到能具体到"可以去现场验证"为止。

追问话术示例：
- 用户不够具体 → "你能描述一个具体的人吗？他叫什么、在哪工作、每天什么环节最头疼？"
- 场景不够具体 → "这个问题在什么时间、什么地点、什么情况下发生？是每天还是偶尔？"
- 痛点不够具体 → "具体是什么东西坏掉了、卡住了、慢了？用户现在的替代方案是什么？"

### 第二步：KANO 类型判断

判断这个功能属于哪一类：

| 类型 | 信号 | 判断 | 策略建议 |
|------|------|------|---------|
| **必备**（没有就愤怒）| 缺失时用户强烈不满 | 必须做，但超出不加分 | 做到及格线即可，不要过度投入 |
| **期望**（越好越满意）| 做得越好越高兴 | 值得持续投入 | 这是核心竞争区，值得打磨 |
| **魅力**（意外惊喜）| 有了惊喜，没有不在意 | 差异化机会 | 可以作为卖点，但不可作为唯一价值 |
| **无差异**（有没有一样）| 用户根本不在意 | 不要做 | 删掉或暂缓 |
| **反向**（做了反而烦）| 用户不希望有这个 | 绝对不做 | 立刻砍掉 |

**判断方法：** 问用户"如果这个功能消失了，用户会怎么反应？"
- 强烈不满 → 必备
- 有些失望 → 期望
- 不在意 → 无差异（这是最常见的陷阱，很多"创新"死在这里）

如果用户无法判断，建议用"反向问卷法"：
1. 如果有这个功能，你觉得用户会？(很开心 / 还行 / 无所谓)
2. 如果没有这个功能，你觉得用户会？(很愤怒 / 有点失望 / 无所谓)

### 第三步：价值护城河检验

这个产品给用户创造了几层价值？

| 价值层 | 含义 | 可替代性 | 检验问题 |
|--------|------|---------|---------|
| **功能价值** | 解决具体问题 | 最容易被复制 | "别人如果做同样的功能，用户会切换吗？" |
| **情绪价值** | 用户使用时的感受 | 需要真心，用户感受得出来 | "用户用的时候会觉得什么？省心？被理解？有面子？" |
| **资产价值** | 用得越久越难离开 | 数据、习惯、关系沉淀——最难被替代 | "用户用了一年后，还会因为什么留下来？" |

**只有功能价值的产品容易陷入价格战。** 检验：除了"解决问题"，用户还会因为什么而留下来？

如果三个价值层只有功能价值有内容 → 在报告中标注"护城河不足，建议补充情绪价值或资产价值的设计"。

### 第四步：输出深度分析报告

运行完毕后，输出以下格式的结论：

```
## 需求深度分析报告

### 总体判断
**结论：** ✅ 可以推进 / ⚠️ 需要调整后推进 / 🛑 暂停，重新调研

### 三要素精度
| 要素 | 评估 | 说明 |
|------|------|------|
| 用户 | [达标/需补充] | [具体说明] |
| 场景 | [达标/需补充] | [具体说明] |
| 痛点 | [达标/需补充] | [具体说明] |

### 需求类型（KANO）
**类型：** [必备 / 期望 / 魅力 / 无差异 / 反向]
**判断依据：** [如果功能消失，用户会____]
**策略建议：** [对应的策略]

### 价值护城河
| 价值层 | 评估 | 说明 |
|--------|------|------|
| 功能价值 | [有/无] | [具体说明] |
| 情绪价值 | [有/无] | [具体说明] |
| 资产价值 | [有/无] | [具体说明] |
**护城河强度：** [强 / 中 / 弱]

### 主要风险（最多3条）
1. [最关键的疑点]
2. [次要疑点]
3. [第三疑点]

### 建议下一步（最多2个行动）
1. [一个具体行动]
2. [一个具体行动]
```

## 常见陷阱

| 陷阱 | 表现 | 破解方法 |
|------|------|---------|
| **功能堆砌** | "我们可以加XX、XX、XX功能" | 回到三要素：每个功能服务的是哪个用户的哪个痛点？ |
| **伪魅力型** | "这个功能用户会很惊喜" | 魅力型的前提是"有了惊喜，没有不在意"。如果用户没它也行，那是无差异。 |
| **护城河幻觉** | "我们先做功能，沉淀以后再说" | 没有资产价值设计的产品，用户随时可以走。在第一天就要想清楚。 |
