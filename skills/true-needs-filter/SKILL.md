# True Needs Filter（真需求快速过滤）

> 来源框架：梁宁《真需求》（新星出版社，2024）
> 这是 true-needs-analysis 工具包的第一步——30秒快速判断。

## 核心原则

```
真需求 = 用户 + 场景 + 痛点
三者都必须具体、可观察，不能是推断
```

大多数产品失败不是因为做得不好，而是因为建立在了**想象的需求**上。这个skill只做一件事：**用最快的速度告诉你，这个需求是不是想象出来的。**

## 使用前提

**只在用户主动要求快速验证时运行本 skill。**
- ✓ "帮我快速判断这个想法靠不靠谱"
- ✓ "值不值得做"
- ✓ "这个需求是真的吗"
- ✗ 用户想要深度分析 → 建议使用 true-needs-deep
- ✗ 用户说"我想做 X"但意图是问怎么做 → 不要拦截，直接帮他做

## 运行流程

### 只做一件事：跑这三个问题

向用户提出以下三个问题，**等待回答后再继续**：

1. **用户是谁？** 你能描述一个具体的人，他/她正处于什么处境吗？
   - 不是"忙碌的职场人"，而是"仓库里负责对账的王姐，每天下班前要手工核两遍出库单"
   - 检验标准：能不能去找到这个具体的人

2. **痛苦在哪？** 有没有你亲眼观察到、或者看到有人抱怨过的具体行为？
   - 论坛帖子、客服记录、朋友吐槽都算
   - "逻辑上应该会有这个问题"不算——必须是观察到的，不是推断的

3. **有没有人在绕路解决这个问题？** 目前用户怎么凑合处理这件事的？
   - 有人为此付过钱吗？
   - 如果没人在绕路，说明痛点可能不够痛

### 评估回答

| 三个问题的回答质量 | 结论 | 下一步建议 |
|----------------|------|-----------|
| 三个都有具体、可观察的答案 | ✅ 通过快速过滤 | 可以继续推进，如需深度分析可使用 true-needs-deep |
| 有1-2个模糊或无法回答 | ⚠️ 存在风险 | 告知用户具体哪里需要调查，建议补齐后再推进 |
| 三个都答不上来，或全是推断 | 🛑 想象中的需求 | 建议先去现场观察，收集真实证据后再回来 |

## 输出格式

给出评估后，输出以下格式的结论（简洁，不超过150字）：

```
## 快速过滤结论

**判断：** ✅ 可以推进 / ⚠️ 需要先调查 / 🛑 暂停，重新调研

**三问结果：**
- 用户：[具体 / 模糊 / 缺失]
- 痛点：[观察到 / 部分推断 / 纯推断]
- 绕路行为：[有 / 不确定 / 没有]

**最关键的风险：** [一句话指出最大的问题]

**建议下一步：** [一个具体行动]
```

## 红旗词

需求描述中出现以下词语，大概率是想象出来的：

> "应该" · "显然" · "大家都" · "逻辑上说得通" · "用户应该会需要"

遇到这些词时，在评估中明确指出"检测到红旗词，该判断可能是推断而非观察"。

## 常见合理化借口（供参考）

| 说法 | 实际问题 |
|------|--------|
| "我了解我的用户" | 了解 ≠ 观察。有具体行为证据吗？ |
| "竞争对手都在做" | 他们可能也做错了。看用户留存数据。 |
| "用户说他们需要这个" | 用户说想要 ≠ 真的会用。看行为。 |
| "逻辑上说得通" | 想象中的需求逻辑上永远说得通，这正是陷阱所在。 |
